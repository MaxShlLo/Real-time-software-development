# Захист лабораторних №1 і №2 з ROS 2

Файл для телефона. Пошук за словами **Лаба 1**, **Лаба 2**, **Файли**, **Терміни**, **Контрольні**, **Помилки**, **Телефон** веде до потрібного розділу. Команди в блоках можна копіювати по рядку.

**Лаба 1 за 20 секунд.** Підготував ROS 2 Lyrical у Docker, зібрав пакет lab1_pkg, зареєстрував звичайний вузол як компонент і створив два керовані вузли. Під час запуску програма сама переводить їх з Unconfigured через Inactive в Active. Обидва обслуговує один SingleThreadedExecutor.

**Лаба 2 за 30 секунд.** DataFilter приймає текст лише за наявності слухачів, переводить його у верхній регістр і публікує результат. QoS задає історію та правила доставки. Сервіс скидає лічильник, Action обробляє масив із прогресом, а Type Adapter дає двом компонентам обмінюватися хмарою PCL напряму в одному процесі.

## Лаба 1 — запуск і показ

Відкрий Docker Desktop. У **PowerShell** зайди в папку лаби й перевір Docker. Команду build вводь, якщо образу ще немає або змінився Dockerfile.

~~~powershell
Set-Location -LiteralPath 'C:/Study/Розробки ПЗ СРЧ/lab1'
docker info
docker build -t ros2_lab1_image .
~~~

У **PowerShell** запусти контейнер. Ім’я ros2_lab1_defense використовується нижче для відкриття другої вкладки.

~~~powershell
docker run -it --rm --name ros2_lab1_defense --mount "type=bind,source=$($PWD.Path)/ros2_ws,target=/ros2_ws" ros2_lab1_image
~~~

Після run ти в **Bash контейнера**. Збери пакет, якщо збірки ще немає або змінювався C++. Для вже зібраного пакета можна одразу виконати source і ros2 run.

~~~bash
cd /ros2_ws
colcon build --symlink-install
source /ros2_ws/install/setup.bash
ros2 run lab1_pkg lifecycle_nodes
~~~

Очікуй **Summary: 1 package finished** після збірки. Після run обидва вузли виводять **Unconfigured**, потім **on_configure → Inactive** і **on_activate → Active**. Це основний показ зі звіту. Програма далі чекає у spin. Ctrl+C зупиняє її.

### Лаба 1 — якщо попросять показати переходи вручну

Залиш lifecycle_nodes працювати. У **другій вкладці PowerShell** зайди в той самий контейнер.

~~~powershell
docker exec -it ros2_lab1_defense /entrypoint.sh bash
~~~

У **Bash другої вкладки**:

~~~bash
source /ros2_ws/install/setup.bash
ros2 node list
ros2 lifecycle nodes
ros2 lifecycle get /lc_node_1
ros2 lifecycle get /lc_node_2
ros2 lifecycle list /lc_node_1
~~~

У get очікуй **active [3]** в обох. list показує переходи, доступні з поточного стану. На першому вузлі можна пройти повний цикл і повернутися в Active.

~~~bash
ros2 lifecycle set /lc_node_1 deactivate
ros2 lifecycle get /lc_node_1
ros2 lifecycle set /lc_node_1 cleanup
ros2 lifecycle get /lc_node_1
ros2 lifecycle set /lc_node_1 configure
ros2 lifecycle set /lc_node_1 activate
ros2 lifecycle get /lc_node_1
~~~

Результат за порядком — **Inactive → Unconfigured → Inactive → Active**. Другий вузол лишається Active.

### Лаба 1 — якщо попросять показати компонент

У першій вкладці зупини lifecycle_nodes через Ctrl+C. Запусти стандартний процес для компонентів із явним ім’ям.

~~~bash
ros2 run rclcpp_components component_container --ros-args -r __node:=lab1_components
~~~

У **Bash другої вкладки**:

~~~bash
ros2 component types
ros2 component load /lab1_components lab1_pkg lab1_namespace::ComponentNode
ros2 component list
ros2 node list
~~~

types показує зареєстровані класи. load завантажує клас із нашої спільної бібліотеки. У першій вкладці очікуй **The component node has been successfully initialized**, у списках — **/my_component_node**. У звіті показано запуск lifecycle_nodes. Ця демонстрація перевіряє інший файл, component_node.cpp.

Команда, якою початково створювався шаблон пакета, потрібна лише для пояснення етапу створення. Папка пакета вже є.

~~~bash
cd /ros2_ws/src
ros2 pkg create --build-type ament_cmake --dependencies rclcpp rclcpp_components --node-name component_node lab1_pkg
~~~

## Лаба 2 — підготовка трьох вкладок

**А** — вузол або сервер. **Б** — слухач. **В** — публікація, виклик сервісу або діагностика. Це три оболонки в одному Docker-контейнері. Ctrl+C у Bash зупиняє поточну команду. exit у початковій оболонці А завершує контейнер.

У **PowerShell, А**. Виконуй build за першого запуску або після зміни Dockerfile.

~~~powershell
Set-Location -LiteralPath 'C:/Study/Розробки ПЗ СРЧ/lab2'
docker info
docker build -t ros2_lab2_image .
docker run -it --rm --name ros2_lab2_screens -e ROS_DOMAIN_ID=42 --mount "type=bind,source=$($PWD.Path)/ros2_ws,target=/ros2_ws" ros2_lab2_image
~~~

У **Bash, А**. Якщо пакети вже зібрані й код не змінювався, достатньо source.

~~~bash
cd /ros2_ws
colcon build --symlink-install
source /ros2_ws/install/setup.bash
~~~

Після збірки очікуй **Summary: 2 packages finished**. У **PowerShell кожної вкладки Б і В** відкрий оболонку в тому самому контейнері.

~~~powershell
docker exec -it ros2_lab2_screens /entrypoint.sh bash
~~~

У **Bash кожної нової вкладки** підключи пакети.

~~~bash
source /ros2_ws/install/setup.bash
~~~

Усі подальші команди ROS 2 — у Bash. Якщо контейнер з таким ім’ям вже працює, відкрий оболонку через exec. Перевірити запущені контейнери можна в PowerShell командою docker ps, усі контейнери — docker ps -a, образи — docker image ls.

### 1. Верхній регістр

**А** — запусти фільтр і залиш працювати.

~~~bash
ros2 run lab2_pkg data_filter
~~~

**Б** — запусти слухача й дочекайся **Input subscription enabled** у А.

~~~bash
ros2 topic echo /uppercase_topic std_msgs/msg/String --qos-reliability reliable --qos-durability transient_local --qos-depth 10
~~~

**В** — команди публікації зі звіту. Для стислого показу достатньо першої та останньої.

~~~bash
ros2 topic pub --once /input_topic std_msgs/msg/String "{data: 'Hello ROS 2'}"
ros2 topic pub --once /input_topic std_msgs/msg/String "{data: 'Hello 2'}"
ros2 topic pub --once /input_topic std_msgs/msg/String "{data: 'Привіт 2'}"
ros2 topic pub --once /input_topic std_msgs/msg/String '{data: "Привіт з знаком !"}'
~~~

--once публікує один раз. {data: …} задає поле повідомлення у форматі YAML. У Б очікуй **HELLO ROS 2**, **HELLO 2**, **ПРИВІТ 2**, **ПРИВІТ З ЗНАКОМ !**. Одинарні лапки зовні останнього аргумента захищають знак ! від підстановки історії Bash.

### 2. Ледача підписка

Натисни Ctrl+C у **Б**, залиш А працювати. У **В** перевір вузол.

~~~bash
ros2 node info /data_filter
~~~

В А з’являється **Input subscription disabled**, а в секції **Subscribers** вузла відсутня /input_topic. Вихідний видавець залишається доступним. Коли слухач повернеться, фільтр знову підпишеться на вхід.

### 3. Останнє повідомлення

Фільтр в А продовжує працювати. У **Б** повторно відкрий слухача, у В нічого не публікуй.

~~~bash
ros2 topic echo /uppercase_topic std_msgs/msg/String --qos-reliability reliable --qos-durability transient_local --qos-depth 10
~~~

Новий слухач одразу отримає **ПРИВІТ З ЗНАКОМ !**, якщо саме цей рядок був останнім. Глибина **1** встановлена у видавця. Глибина **10** в команді належить слухачеві. Перед пунктом 4 зупини слухача у Б.

### 4. Перевизначення QoS

**А** — Ctrl+C і запуск фільтра з YAML.

~~~bash
ros2 run lab2_pkg data_filter --ros-args --params-file /ros2_ws/install/lab2_pkg/share/lab2_pkg/config/qos_overrides.yaml
~~~

**В** — перевір профіль видавця й значення параметра.

~~~bash
ros2 topic info /uppercase_topic --verbose
ros2 param get /data_filter qos_overrides./uppercase_topic.publisher.depth
~~~

Очікуй **BEST_EFFORT**, **VOLATILE**, **KEEP_LAST (3)** і параметр **3**. --ros-args починає секцію аргументів ROS 2, --params-file читає YAML під час запуску. Якщо попросять послухати тему з новим профілем, у Б запусти сумісного слухача й опублікуй рядок у В.

~~~bash
ros2 topic echo /uppercase_topic std_msgs/msg/String --qos-reliability best_effort --qos-durability volatile
~~~

### 5а. Асинхронний ResetFilter

**А** — Ctrl+C і знову звичайний фільтр. Якщо в Б працює слухач із пункту 4, зупини його.

~~~bash
ros2 run lab2_pkg data_filter
~~~

**Б** — відкрий слухача. Дочекайся **Input subscription enabled** у А.

~~~bash
ros2 topic echo /uppercase_topic std_msgs/msg/String --qos-reliability reliable --qos-durability transient_local
~~~

**В** — надішли три повідомлення. Коли Б виведе ONE, TWO і THREE, двічі запусти клієнта.

~~~bash
ros2 topic pub --once /input_topic std_msgs/msg/String "{data: 'one'}"
ros2 topic pub --once /input_topic std_msgs/msg/String "{data: 'two'}"
ros2 topic pub --once /input_topic std_msgs/msg/String "{data: 'three'}"
~~~

~~~bash
ros2 run lab2_pkg reset_filter_client
ros2 run lab2_pkg reset_filter_client
~~~

Перший виклик повертає **success=true previous_count=3**, другий — **previous_count=0**. Якщо вже було більше публікацій, спочатку виклич клієнта для обнулення. Сервіс скидає лічильник оброблених рядків. Видавець зберігає свою історію окремо.

### 5б. Інтроспекція

Зупини слухача /uppercase_topic у **Б**. Фільтр в А залиш працювати. У Б відкрий події сервісу.

~~~bash
source /ros2_ws/install/setup.bash
ros2 topic list --include-hidden-topics | grep --color=never -Fx /reset_filter/_service_event
ros2 topic echo /reset_filter/_service_event lab2_interfaces/srv/ResetFilter_Event | grep --line-buffered -E 'event_type:|success:|previous_count:'
~~~

Коли echo працює, у **В** виклич клієнта.

~~~bash
ros2 run lab2_pkg reset_filter_client
~~~

Очікуй події та відповідь **success: true**, **previous_count: 0**. Коди подій **0** — клієнт надіслав запит, **1** — сервер отримав запит, **2** — сервер надіслав відповідь, **3** — клієнт отримав відповідь. На скріні звіту видно 1, 2 і 3. Символ | передає текст у grep. -Fx шукає точний рядок, -E залишає рядки, що містять будь-яке з трьох полів, а --line-buffered показує їх одразу. Зупини echo у Б після показу.

### 5в. Таймаут

**А** — зупини фільтр і запусти його зі штучною затримкою 350 мс.

~~~bash
ros2 run lab2_pkg data_filter --ros-args -p reset_delay_ms:=350
~~~

**В** — спочатку короткий таймаут. echo $? вводь одразу після команди клієнта. Потім запусти клієнта з довшим таймаутом.

~~~bash
ros2 run lab2_pkg reset_filter_client --ros-args -p timeout_ms:=50
echo $?
ros2 run lab2_pkg reset_filter_client --ros-args -p timeout_ms:=1500
~~~

Перший виклик виведе **Response timeout after 50 ms** і код **3**. Другий — **success=true**. -p задає параметр вузла. Таймаут завершує очікування на стороні клієнта, а сервер може виконати вже прийнятий запит.

### 6. Action ProcessArray

**А** — Ctrl+C на фільтрі та запуск Action-сервера.

~~~bash
ros2 run lab2_pkg array_processor
~~~

**В** — надішли ціль і покажи проміжний прогрес.

~~~bash
ros2 action send_goal /process_array lab2_interfaces/action/ProcessArray "{data: [1.0, -2.0, 3.5], delay_ms: 300}" --feedback
~~~

Сервер підносить числа до квадрата в робочому потоці. Затримка 300 мс перед кожним елементом робить прогрес помітним. Клієнт покаже **33,3%, 66,7%, 100%**, результат **[1.0, 4.0, 12.25]** і кінцевий статус **SUCCEEDED**. Зупини сервер в А після показу.

### 7. Type Adapter і хмара точок

**А** — режим внутрішньопроцесної передачі.

~~~bash
ros2 launch lab2_pkg point_cloud.launch.py intra_process:=true
~~~

Знайди CLOUD_PUB і CLOUD_SUB з однаковим **seq**. У межах цієї пари збігаються **object** і **data**. Видно **points=1000**, **valid=true**, **to_ros=0 from_ros=0**. Для цієї перевірки залиш лише два компоненти. Якщо запустити зовнішній echo, він запросить повідомлення PointCloud2.

**А** — Ctrl+C, далі контрольний режим.

~~~bash
ros2 launch lab2_pkg point_cloud.launch.py intra_process:=false
~~~

Ті самі компоненти знову в одному процесі. Тепер видно **ADAPTER**, обидва лічильники перетворень зростають, **valid=true**. У **В** можна прочитати ширину одного ROS-повідомлення.

~~~bash
ros2 topic echo /point_cloud sensor_msgs/msg/PointCloud2 --field width --once
~~~

Результат **1000**. --field вибирає одне поле, --once завершує слухача після одного повідомлення.

## Файли — що відкрити, якщо попросять показати код

У кожній лабі Dockerfile та entrypoint.sh лежать у корені, а C++ і конфігурація — у відповідних пакетах під ros2_ws/src.

### Файли лаби 1

- **lifecycle_nodes.cpp** — головний файл показу. Клас MyLifecycleNode успадковує rclcpp_lifecycle::LifecycleNode. on_configure, on_activate, on_deactivate та on_cleanup пишуть у журнал і повертають SUCCESS. У main створюються lc_node_1 і lc_node_2. Виклики trigger_transition виконують configure для обох, потім activate для обох. main грає роль простого супервізора під час запуску. Далі executor.add_node і spin обслуговують обидва вузли в одному потоці.
- **component_node.cpp** — окремий компонент lab1_namespace::ComponentNode. Успадковує rclcpp::Node, приймає NodeOptions, задає ім’я my_component_node і виводить лог при завантаженні. Макрос RCLCPP_COMPONENTS_REGISTER_NODE реєструє клас для завантаження. Компонент збирається у .so. Запуск lifecycle_nodes його не створює.
- **CMakeLists.txt** — add_library(... SHARED ...) збирає компонент, rclcpp_components_register_nodes додає його до індексу компонентів, add_executable збирає lifecycle_nodes. install розкладає бібліотеку й виконуваний файл так, щоб їх знайшли ros2 component і ros2 run.
- **package.xml** — назва й метадані пакета, тип збірки ament_cmake та залежності ROS 2. Dockerfile бере образ ros:lyrical, додає інструменти збирання та задає /ros2_ws. entrypoint.sh підключає /opt/ros/$ROS_DISTRO/setup.bash і запускає Bash або передану команду через exec "$@".

### Файли лаби 2

- **data_filter.cpp, рядки 25–75 і 124–140** — параметри назв тем, QoS, matched_callback, сервіс і перетворення тексту. При першому сумісному слухачеві створюється підписка на /input_topic. При нулі слухачів subscription_.reset() видаляє її. Видавець /uppercase_topic за замовчуванням має KeepLast(1), Reliable, Transient Local. process_message декодує UTF-8, переводить літери у верхній регістр через локаль C.UTF-8, кодує назад, публікує і збільшує processed_count_. Сервіс читає старий лічильник і скидає його. reset_delay_ms за замовчуванням **0**.
- **config/qos_overrides.yaml** — змінює профіль видавця /uppercase_topic під час запуску на глибину **3**, **best_effort**, **volatile**. Можливість змінювати ці три політики явно дозволено в C++ через QosOverridingOptions.
- **srv/ResetFilter.srv** у lab2_interfaces — порожній запит. Відповідь містить bool success, uint64 previous_count, string message. З цього опису під час збірки генеруються ROS-типи, включно з типом події ResetFilter_Event.
- **reset_filter_client.cpp** — шукає сервіс до **3000 мс**, чекає відповідь за замовчуванням **2000 мс**. Відправляє async_send_request, головний потік чекає на future.wait_for, окремий spin-потік обробляє відповідь. Після таймауту remove_pending_request очищає запис про запит. Коди **0** — успіх, **1** — помилка, **2** — сервіс недоступний, **3** — таймаут відповіді. configure_introspection з CONTENTS викликається і тут, і в data_filter.cpp.
- **action/ProcessArray.action** у lab2_interfaces — ціль data і delay_ms, результат processed_data і processed_count, проміжні processed_count, total_count та progress. Роздільники --- відокремлюють три частини.
- **array_processor.cpp** — сервер /process_array. Перевіряє масив і приймає по одній активній цілі. Запускає обчислення в окремому std::thread, підносить числа до квадрата і після кожного елемента надсилає feedback. Публікує кінцевий результат через succeed, підтримує скасування й при завершенні приєднує робочий потік. У демо **300 мс** задається клієнтом, а ліміт у коді — **1000 мс на елемент**.
- **point_cloud_components.cpp** — CloudPublisher створює хмару з **1000 точок кожні 500 мс** за наявності слухача. Віддає unique_ptr через std::move. CloudSubscriber отримує хмару, перевіряє координати й структуру, друкує seq, object, data та valid. Лічильники to_ros і from_ros показують виклики адаптера.
- **include/lab2_pkg/point_cloud_adapter.hpp** — TypeAdapter між pcl::PointCloud<pcl::PointXYZ> і sensor_msgs::msg::PointCloud2. convert_to_ros_message пакує координати та метадані, convert_to_custom читає ROS-повідомлення назад у PCL. Це місце, де зростають лічильники перетворень.
- **launch/point_cloud.launch.py** — завантажує два компоненти в один процес і передає їм use_intra_process_comms зі значення intra_process. За замовчуванням **true**. **launch/lab2.launch.py** додатково запускає фільтр і Action.
- **CMakeLists.txt і package.xml** є в обох пакетах. lab2_interfaces генерує інтерфейси, lab2_pkg збирає вузли, реєструє компоненти, встановлює YAML і launch-файли. Dockerfile готує ROS 2, компілятор, colcon і заголовки PCL. entrypoint.sh підключає базовий ROS 2. **test/** містить чотири скрипти перевірки, які наведені вище.

## Терміни — коротко своїми словами

### Лаба 1 і спільне середовище

- **ROS 2** — набір бібліотек і засобів, за допомогою яких вузли робота обмінюються даними та виконують задачі. **Lyrical** — дистрибутив ROS 2, а **rclcpp** — його клієнтська бібліотека для C++.
- **Вузол (node)** — одиниця логіки з іменем у графі ROS 2. **Граф ROS 2** — вузли та їхні теми, сервіси й дії. **Discovery** — механізм, через який вони знаходять одне одного. **ROS_DOMAIN_ID** розділяє такі групи.
- **Dockerfile** — рецепт створення образу. **Образ** — готовий шаблон із залежностями. **Контейнер** — екземпляр образу, який можна запустити. **Bind mount** підключає справжню папку Windows як /ros2_ws у контейнері. **WSL 2** може слугувати Linux-бекендом Docker Desktop. Запрошення root@… після docker run належить Bash усередині контейнера.
- **docker build** готує образ. **docker run** створює й запускає контейнер. **docker exec** запускає команду в контейнері, який вже працює. **-it** дає інтерактивну консоль, **--rm** видаляє контейнер після завершення, **--name** задає його ім’я, **-e** передає змінну середовища.
- **Workspace** — робоча папка ROS. У **src** лежать пакети, **build** містить проміжні файли, **install** — результати для запуску, **log** — журнали збірки. **colcon** збирає пакети з урахуванням залежностей. **ament_cmake** інтегрує пакет ROS 2 із CMake. **--symlink-install** використовує символічні посилання де можливо. Після зміни C++ потрібна збірка.
- **source setup.bash** налаштовує поточну оболонку, щоб вона бачила пакети та бібліотеки. Системний setup підключає базовий ROS 2. Workspace setup підключає наші зібрані пакети. У кожній новій оболонці його виконують знову.
- **Компонент** — вузол, який можна завантажити зі спільної бібліотеки під час виконання. **NodeOptions** передає параметри створення вузла. **Namespace** у C++ групує імена класів. **Component container** — процес, що завантажує вузли-компоненти. Docker-контейнер містить ці процеси й термінали.
- **Callback** — функція, яку викликає ROS 2 у відповідь на подію. **Executor** планує виконання callback’ів. **SingleThreadedExecutor** виконує їх по одному. **spin** запускає цикл обробки подій, **spin_once** робить один крок очікування й обробки.
- **Lifecycle Node** — вузол із керованими станами. **FSM** — скінченний автомат зі станами та дозволеними переходами. **Transition** — перехід, наприклад configure або activate. **Супервізор** координує переходи вузлів.
- **Unconfigured** — початковий стан без підготовленої конфігурації. **Inactive** — вузол сконфігурований і чекає активації. **Active** — робочий стан. **Finalized** — завершений стан після shutdown. configure веде в Inactive, activate — в Active, deactivate — назад в Inactive, cleanup — в Unconfigured.

### Лаба 2

- **Topic** — іменований канал повідомлень. **Publisher** пише в тему, **subscriber** читає. Тип повідомлення задає його поля. У std_msgs/msg/String є поле data.
- **Service** — короткий запит і відповідь. **Server** приймає запит, **client** викликає. **Action** — інтерфейс для довшої операції з ціллю (**goal**), проміжним прогресом (**feedback**), статусом, можливістю скасувати (**cancel**) і кінцевим результатом (**result**). У ROS 2 Action використовує сервіси send_goal, cancel_goal, get_result і теми feedback та status.
- **QoS** — політики обміну. **History** задає, скільки зберігати. **KeepLast(N)** лишає до N зразків, **KeepAll** зберігає доступну історію в межах ресурсів, **Depth** — значення N для KeepLast. **Reliable** намагається забезпечити доставку з повторними передачами за потреби, **Best Effort** допускає втрати. **Transient Local** дозволяє отримати історію від видавця, який ще працює. **Volatile** передає нові повідомлення.
- **Deadline** — очікувана межа інтервалу між повідомленнями. **Lifespan** — час, протягом якого повідомлення чинне. **Liveliness** — правила визначення, чи видавець досі активний.
- **Requested/Offered** — слухач запитує певну політику, видавець пропонує свою. Для сумісності пропозиція має задовольняти запит за відповідними політиками. Видавець Best Effort і слухач Reliable несумісні. Reliable-видавець може працювати з Best Effort-слухачем, якщо інші політики сумісні. Глибини черг можуть відрізнятися.
- **Ледача підписка** — фільтр читає вхід лише за наявності сумісного слухача виходу. **matched_callback** повідомляє про зміну кількості сумісних підписників. **QoS override** — перевизначення дозволених політик через параметри вузла.
- **Асинхронний запит** відправляється одразу й повертає **future** для майбутньої відповіді. **Таймаут** — межа очікування. **Deadlock** — взаємне блокування, наприклад, коли єдиний потік executor’а чекає на відповідь, яку сам мав би обробити. **Callback group** задає правила одночасного виконання callback’ів. Mutually Exclusive виконує по одному в групі, Reentrant допускає одночасне виконання.
- **Інтроспекція** — спостереження за обміном запитами й відповідями. **CONTENTS** додає в події метадані та вміст. **/_service_event** — суфікс прихованої теми подій сервісу. **CLI** — інтерфейс командного рядка, наприклад ros2 topic або ros2 action.
- **UTF-8** — кодування тексту, в якому українська літера може займати кілька байтів. **Локаль C.UTF-8** дає нашому фільтру правила обробки символів після декодування.
- **PCL** — бібліотека для хмар точок. **PointCloud2** — стандартне ROS-повідомлення з описом полів, розмірів і буфером даних. **Type Adapter** — міст між C++-типом і ROS-повідомленням, описаний у REP-2007. **Серіалізація** — пакування повідомлення в байти для обміну. **DDS** — технологія обміну даними, яку можуть використовувати реалізації середнього шару ROS 2.
- **Intra-process** — передача в межах одного процесу. **unique_ptr** — вказівник з єдиним власником. **std::move** дозволяє передати володіння далі. **Zero-copy** у нашому показі означає, що слухач отримав той самий об’єкт і масив точок без копіювання на цій ділянці. Дивимось збіг адрес для одного seq і нульові лічильники перетворень.

## Контрольні — короткі відповіді

### Лаба 1

1. **Навіщо компоненти й чим ризикуємо?** Вузли можна динамічно завантажувати в один процес. За налаштованого intra-process можна зменшити витрати на передачу. Спільний процес має спільну долю при аварії, а довгий callback може затримати інші callback’и в одному потоці.
2. **Як експортувати компонент?** Клас приймає rclcpp::NodeOptions і надає інтерфейс вузла. У нас це успадкування від rclcpp::Node. Макрос у C++ реєструє клас, CMake збирає SHARED-бібліотеку та реєструє її компонент. Після install і source процес може знайти й завантажити клас.
3. **Чим небезпечний spin_once в конструкторі?** Executor може викликати callback, поки об’єкт ще частково ініціалізований. Очікування у конструкторі також може заблокувати створення вузла або завадити його завантаженню. У нас spin викликається в main після створення обох вузлів і переходів.
4. **Які стани й переходи?** Unconfigured → configure → Inactive → activate → Active. Далі deactivate повертає в Inactive, cleanup — в Unconfigured. Shutdown веде у Finalized.

### Лаба 2

1. **Як виникає deadlock при виклику сервісу з таймера?** Якщо callback таймера чекає, єдиний потік не може обробити відповідь. Можна надіслати асинхронний запит і повернутися з callback або використати кілька потоків executor’а та групи, які дозволяють одночасну обробку. У нашому клієнті очікування відбувається поза spin-потоком. Різні групи самі по собі додаткового потоку не створюють.
2. **Як перевірити сумісність QoS?** Перевірити, чи кожна відповідна політика видавця задовольняє вимогу підписника. Reliable-видавець підходить Best Effort-слухачеві, а Best Effort-видавець не задовольняє Reliable. Історія для пізнього слухача потребує Transient Local з обох боків.
3. **Звідки _service_event?** Клієнт і сервер викликають configure_introspection зі станом CONTENTS. ROS 2 формує події й публікує їх у прихованій темі. Власний видавець подій у C++ для цього не створюється.
4. **Навіщо Type Adapter?** Код вузлів працює з природним типом PCL. У межах одного процесу в нашій конфігурації можна передати об’єкт напряму, а для ROS-підписника адаптер формує PointCloud2. Перевіряємо це двома режимами й лічильниками.
5. **Коли Action замість сервісу?** Коли операція тривала і треба бачити стан, прогрес чи мати можливість її скасувати. Скидання лічильника в нас сервіс, обробка масиву з feedback — Action.

## Помилки — що зробити під час показу

- **Docker API / dockerDesktopLinuxEngine** — відкрий Docker Desktop і дочекайся запуску Engine. Перевір docker info у PowerShell.
- **Container name already in use** — подивись docker ps. Якщо потрібний контейнер працює, зайди через docker exec із відповідним іменем. Якщо його видно лише в docker ps -a як зупинений, можна вибрати нове ім’я в --name та використовувати це саме ім’я в docker exec. Після перезавантаження при наявному образі й відсутньому контейнері достатньо docker run.
- **Package not found / The passed message type is invalid** — у поточному Bash повтори source /ros2_ws/install/setup.bash. Якщо файла немає, у /ros2_ws виконай colcon build --symlink-install і повтори source.
- **event not found** при публікації рядка з ! — скопіюй команду з одинарними лапками навколо всього YAML-аргумента з пункту 1.
- **Немає результату з фільтра** — перевір, чи фільтр працює і чи слухач має сумісний QoS. Дочекайся Input subscription enabled перед публікацією. Після YAML-запуску користуйся слухачем із пункту 4 або поверни стандартний запуск.
- **Не видно збереженого рядка** — перевір, чи фільтр не перезапускався між публікацією та новим echo і чи слухач запущений з transient_local.
- **У режимі intra_process:=true лічильник росте** — зупини зовнішній echo /point_cloud і перезапусти обидва компоненти разом. Зіставляй лог видавця й підписника за однаковим seq.
